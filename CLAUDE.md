This file gives Claude Code persistent context for this project. Read it at the start of every session. Update it (especially the Phase Status section) as work progresses, so the next session picks up accurately.

## Project Overview

A custom web app replacing a commercial app the user previously used for designing seed bead patterns (peyote, brick stitch, square stitch, bead looming). Built from scratch — not a clone, not reverse-engineered — based on a feature list and workflow requirements gathered directly from the user. Runs in Safari on iPad (installable to home screen), used for personal, non-commercial purposes only.

## Why This App Exists (origin of requirements)

The prior app's specific pain points that this app must fix:
1. Preferences don't persist across designs — must set grid/tool preferences per-file, every time.
2. No manual control over the order designs are displayed in a library view.
3. Colorways (same pattern, different color mapping) require full duplicate files — wasteful and error-prone.
4. Easy to lose current state — no autosave, must remember to manually duplicate before experimenting.
5. Closing/switching designs takes too many steps.

## Bead Specs (source: official Miyuki site, miyuki-beads.co.jp/english/seed/01.html — verified via screenshot of their official size chart)

| Type | Size | Diameter (mm) | Hole (mm) |
|---|---|---|---|
| Round Rocaille | 11/0 | 2.0 | 0.8 |
| Delica (DB) | 11/0 | 1.6 | 0.8 |

**Known gap, unresolved as of last session:** Miyuki's official chart gives only one diameter figure per bead — no separate width vs. height. Grid rendering needs both (this is what makes peyote/brick rows render as offset rather than square). Secondary, non-Miyuki sources suggest approximate figures below, but these are **not verified against an authoritative source** and should be treated as provisional until confirmed (e.g. by direct caliper measurement or a second manufacturer source):
- Delica 11/0: ~1.6mm wide × ~1.3mm tall (estimated)
- Rocaille 11/0: ~2.0mm wide × ~1.3–1.5mm tall (estimated, rocailles are flatter than their diameter suggests)

Store these as named, easily-editable constants (not hardcoded magic numbers scattered through grid math) so they can be corrected without a rewrite once verified.

## Architecture

Vanilla JS, ES modules, no build step, no framework, no bundler.

```
/src
  /grid          — grid math: peyote/brick/square/loom coordinate generation, bead aspect ratios
  /render        — canvas drawing, pan/zoom, viewport logic
  /tools         — draw, erase, fill, color-replace, cut/copy, mirror (one file per tool)
  /palette       — bead color data (Delica/Rocaille specs, color libraries)
  /storage       — IndexedDB wrapper, save/load, autosave
  /export        — word chart generation, print layout
  /units         — mm <-> inch conversion helpers (display layer only)
  main.js        — app shell, wires modules together, event handling
index.html
style.css
CLAUDE.md        — this file
```

## Dev/Verification Tooling

- No `package.json`/`node_modules` in this repo — `node --test 'src/test/**/*.js'` run directly from the repo root runs the whole `node:test` suite (glob quoted so the shell doesn't expand it; `node --test src/test/` alone fails with `MODULE_NOT_FOUND`, it needs actual file paths).
- Playwright isn't installed locally either, but it's globally npx-cached (confirmed present via `npx --no-install playwright --version`, currently 1.62.x) — `npx playwright ...` resolves fine directly. A plain Node script with `import { chromium } from 'playwright'` does **not** resolve on its own, though — Node's ESM resolver doesn't honor `NODE_PATH` for bare specifiers, so `node script.mjs` fails with `ERR_MODULE_NOT_FOUND` even though the package is genuinely present on disk. Fix: find the cached copy (`find ~/.npm/_npx -maxdepth 4 -iname playwright -type d`, one hashed subdirectory per npx-installed version) and symlink its `node_modules` next to the driver script (`ln -sfn <that path>/node_modules <script dir>/node_modules`) before running — normal Node module resolution then finds it by walking up from the script's own directory. Delete the symlink when done (it's just a bridge to the cache, not a real install). No need to search for or install it each session — the cache doesn't move between sessions on the same machine.
- Standard verification loop used for every phase so far: `python3 -m http.server <port>` from the repo root (serves `index.html` at the repo root directly, no build step), then a throwaway Node driver script using `playwright` to drive headless Chromium against `http://localhost:<port>/`. Exact bead-cell screen coordinates are computed by reimplementing `peyoteCellOriginMm`/`fitViewportToGrid`/`worldToScreen`'s math directly in the driver script (or via dynamic `import()` of the app's own modules in-page), not approximated — see any past phase's Phase Status verification notes for the pattern. Kill the http.server background process when done.

## Best Practices To Follow

- Grid math and tool logic as pure functions (state in, state out) — separate from canvas rendering and DOM/event handling. Keeps core logic testable and reasoning-friendly across sessions.
- Internal units always mm. Conversion to inches happens only at the point of display (readouts, labels) — never propagate converted values back into stored/calculated state.
- One central app-state object; modules read/write through defined functions, not by reaching into each other's internals.
- Comments explain *why*, especially for grid offset math — not restating *what* the code visibly does.
- Commits should map to phase boundaries (see below), so repo history documents the build progression.
- Bead physical specs live as named constants in `/palette`, not inline magic numbers, since at least one dimension is still provisional (see Bead Specs gap above).

## Phase Plan

1. **Phase 1 — Peyote grid engine.** Grid math only: given bead width/height ratio, generate correct offset-row peyote layout, render on canvas, support pinch-zoom/pan. No drawing yet. mm-based internally, inches toggle for size readout (Decision #6) built in from the start.
2. **Phase 2 — Draw + erase.** Tap placement, drag-to-draw (Decision #9), erase, Delica/Rocaille color palettes wired in.
3. **Phase 3 — Undo/redo.** History stack over draw/erase actions (Decision #12). Built as its own phase, ahead of save/load, since it's core drawing-tool functionality tightly coupled to Phase 2's draw/erase — not lumped in with the lower-priority tools in Phase 7.
4. **Phase 4 — Save/load + project library.** Autosave to IndexedDB, reorderable design list (manual ordering), global persistent preferences (fixes prior-app pain point #1 and #2).
5. **Phase 5 — Print/export instructions.** Row-by-row word chart generation, printable layout.
6. **Phase 6 — Colorways.** Same-grid/alternate-palette variant (Decision #8), lightweight relative to a full duplicate (fixes prior-app pain point #3).
7. **Phase 7 — Remaining tools.** Fill, color-replace, cut/copy, mirror, photo trace overlay with adjustable transparency (Decision #10). (The grid/canvas orientation toggle originally listed here was dropped as of the Phase 7 planning session, 2026-08-09 — the user confirmed the underlying complaint was already resolved by the row/col transpose fix done between Phases 5 and 6, and the item was a misunderstanding of that same issue, not a separate need.)
8. **Phase 8 — Side panel layout + custom color palettes.** Restructure the editor from one wrapping top toolbar into a slim top bar + narrow left tool rail + wide right-side color/colorway/photo-trace panel, structurally modeled on the prior app's own layout (screenshot reviewed 2026-08-09) though not its specific icons/styling (not a clone, per this file's Project Overview). Alongside that, replace the placeholder color swatches with a user-built palette — native `<input type="color">` picker + name prompt, stored per bead type in a new `customColors` IndexedDB store — since sourcing the real Miyuki catalogs (900+ SKUs each, no machine-readable hex data) isn't practical; see the Bead Specs section's known gap. Built per `.work/phase-8-implementation-plan.md`, see Phase Status.
9. **Later / optional, not yet scheduled.** Brick/loom grid types (square stitch itself **shipped** — see Phase Status's "Square stitch" entry and `.work/feature-square-stitch-plan.md`; the `resolveGridEngine` resolver it introduced is designed so brick/loom could each be added later as their own third/fourth engine module), cloud sync (Decision #5 — now scoped in `.work/feature-cloud-sync-plan.md`, not yet implemented), native app rebuild if still wanted, tagging or folders in library. Automated import of Loomerly (prior app) exports was attempted and removed — see Phase Status — reverse-engineering the undocumented PDF format proved too fragile for what was actually a one-time migration need; hand-tracing via Photo Trace (Decision #10) is the current path for bringing existing designs in. Worth reopening only if Loomerly turns out to support a more direct/lossless export format (CSV, JSON, flat grid bitmap).

**Bead-type conversion — shipped.** This backlog item (added 2026-08-09) is done — see Phase Status's "Bead Catalog, Cross-Palette Color Copy, Convert Bead Type" entry, built per `.work/feature-bead-catalog-and-conversion-plan.md`. The color-remapping question this note originally flagged as unresolved was answered by making the conversion clone-based (a new design, not an in-place mutation) with an explicit per-color mapping dialog (map onto an existing target-palette color, defaulting to an exact hex match, or copy the color over) rather than any automatic heuristic. The fixed Delica/Rocaille pair this note assumed is also gone — bead types are now a user-editable catalog (see Decision #7's status, superseded).
