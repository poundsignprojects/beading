# Feature Plan — Loomerly Pattern Import

## Context

Backlog item ("ability to import the prior app's exports," CLAUDE.md's Later/optional section), scoped by this plan. The user wants to bring existing peyote designs from Loomerly (a prior/other app they use) into this app, via Loomerly's PDF pattern export — not a phase-plan item, standalone feature.

Grounded in one real sample export the user provided this session (a shaped/tapered odd-count peyote strip, 19 wide × 80 "Height," Miyuki Rocaille 11/0, 5 colors, pointed tips at both ends). That sample is the primary source for everything below; a couple more samples (a plain rectangle with no shaping, and a pattern with a larger color palette) should be gathered before/during build to pressure-test the parser against cases this one sample doesn't cover — see "Open questions."

## What this is not

- Not OCR / image-to-pattern. The PDF's word chart, header stats, and color list are real extractable text — this is a text-format parsing problem, not a vision problem. Decision #10's "photo-to-pattern auto-conversion is not a priority" doesn't apply here.
- Not a general PDF import — this only understands Loomerly's specific export layout (header stats page, picture-chart page, word-chart pages, color-list page). A PDF that isn't shaped like this will fail to parse, with a clear error, not a silent bad import.
- v1 is single-section, peyote-only, one colorway. The sample PDF's own header says "Section 1 of 1" and "Type: Peyote" — both should be read and validated, and anything else (multi-section pieces, other stitch types Loomerly might export) should fail with an explicit "not supported yet" message rather than attempt a wrong import.

## The hard part: reconciling Loomerly's row model with this app's grid

This is the actual risk in this feature — everything else (PDF text extraction, color-code UI, design creation) is mechanical and low-risk by comparison. Worth writing the derivation down now so it doesn't have to be re-derived later, the way this project's row/col axis bugs have had to be re-derived more than once already (see CLAUDE.md's Phase Status history on the grid-orientation transpose and the print row/col bug).

**In this app's own peyote model** (`src/grid/peyote.js`), one physical row (a fixed `col` value, per `peyoteRowCells`) can hold up to `rows` beads — a full row is `rows` beads wide, no inherent gaps. `col` values are offset from their neighbors by half a bead-width automatically (`peyoteCellOriginMm`), which is what produces the brick/zigzag look. The one special case in this app's own exporter (`wordChart.js`) is that physical rows 0 & 1 print combined as one instruction ("Rows 1 & 2"), because they're strung onto the thread together at the very start of a peyote piece before normal weaving begins — every row after that stands alone, each spanning the full `rows` width by itself.

**Loomerly's word chart does not work this way.** In the sample, individual row lines never exceed ~10 beads even deep in the solid body of the piece (e.g. `Row 21 (→) (9)D`, `Row 22 (←) (10)D`, repeating for dozens of rows) — nowhere near the stated Width of 19. But *consecutive odd/even pairs* of Loomerly rows consistently sum to exactly 19 in the solid body (`Row 37 (9)D` + `Row 38 (10)D` = 19; `Row 43 (9)D` + `Row 44 (10)D` = 19). Loomerly's "Row 1&2" is printed pre-combined in the text for the same physical-construction reason this app's exporter combines its first pair — but every subsequent pair (3&4, 5&6, ...) is printed as two separate lines even though it's the same kind of pair.

**Conclusion: Loomerly's "row" = one thread pass (half of one finished row-band); this app's "physical row" (`col`) = one finished row-band, built from two consecutive Loomerly rows interleaved together** — generalizing this app's own rows-1&2 interleave (`interleaveCells` in `wordChart.js`) to *every* consecutive pair on import, not just the first. That means:

- internal `rows` (width axis) = Loomerly's `Width` field directly (19) — no ambiguity here, both apps count bead-positions-across-a-row the same way.
- internal `cols` (height axis) = Loomerly's `Height` field directly (80) — **not** the literal word-chart row count (160). Each of this app's 80 physical rows is reconstructed from one pair of consecutive Loomerly rows: (1,2)→col 0, (3,4)→col 1, (5,6)→col 2, ..., (159,160)→col 79.

**Cross-check against the PDF's own stated finished size** (a good sanity mechanism to keep in the actual importer, not just this derivation): using the provisional Rocaille 11/0 dimensions already in `src/palette/beadSpecs.js` (`widthMm: 2.0`, `heightMm: 1.4`) and `generatePeyoteGrid`'s formula —
- `widthMm = rows * beadHeightMm` = 19 × 1.4 = 26.6mm ≈ 1.05" — close to the PDF's stated **1.2"**.
- `heightMm = cols * beadWidthMm + beadWidthMm/2` = 80 × 2.0 + 1.0 = 161mm ≈ 6.34" — close to the PDF's stated **6.6"**.

Both are in the right ballpark (the residual gap is consistent with this app's own flagged *provisional, unverified* bead-height estimate — see CLAUDE.md's Bead Specs gap). If `cols` were instead 160 (the literal word-chart row count, no pairing), the predicted height would be ~12.6" — nowhere close to the stated 6.6". This is real evidence for the pairing model, not just plausible-sounding reasoning, and the importer should perform this exact comparison at import time as a built-in sanity check (warn, don't block, if it's off by more than a wide tolerance — same "clear notice, not a hard stop" philosophy as Phase 5/6's other warnings).

**Confirmed with much stronger evidence from two additional real samples** (a solid 30×40 white rectangle, and the same 30×40 rectangle in a 3-color tessellation pattern — both gathered this session): every single non-combined word-chart line in both files is exactly 15 beads (half of the stated Width, 30) for the *entire* file, no exceptions, and `Row 1&2` combined is exactly 30 (a full row). `rows(30) × cols(40) = 1,200` matches the header's stated `Total beads: 1,200` **exactly** — not approximately close the way the first sample's finished-size check was, but an exact match, because a solid rectangle has every cell occupied so the arithmetic has nowhere to hide an error. This is materially stronger confirmation than the original finished-size cross-check alone. The colored variant additionally validates multi-color run-list parsing (three interleaved colors per row) under this same confirmed geometry, with color counts (350+472+378=1,200) matching exactly too.

**New finding from these two samples: the color list's `"Miyuki [Type] 11/0 (M)"` header line is not always present.** Both rectangle samples' color-list pages start directly at `A 01 White Count: 1,200` / `A 01 White / B 02 Black / C 03 Grey`, with no bead-type header line above the entries — unlike the first (tapered) sample, which had one. Bead-type detection can't be a hard requirement on that line existing. **Revised approach**: compute the predicted finished size for *both* `delica11` and `rocaille11` against the PDF's stated finished size, default to whichever is closer, but always show the guess (and let the user override it) on the preview screen rather than silently trusting either a present header line or the size-based guess alone. (For the white rectangle: Delica predicts ~1.54"×2.55" vs. the stated 1.6"×2.7" — closer; Rocaille predicts ~1.65"×3.19" — further off on height. Delica is the better guess here, and the parser should still read the header line when it *is* present and prefer it over the size-based guess when both exist.)

**A third real sample (gathered this session, a multi-taper Delica lattice/tessellation piece — 55×89, 4 colors, genuine internal negative space, not a solid rectangle) resolved one of these and narrowed the other:**

- **Interior blanks are explicitly printed as their own `-` run — no inference needed there at all.** E.g. `Row 162 (←) (1)B, (2)D, (4)B, (2)D, (1)B, (1)C, (1)A, (1)C, (1)-, (3)C, (1)B, (2)D, (4)B, (2)D, (1)B` sums to exactly 27 (this piece's full half-width) including the `(1)-` — a genuinely blank cell sitting between two colored runs, printed in place just like a real run. This is new information the earlier tapered sample didn't reveal (it never had an interior gap, only short edge totals) and it removes a whole category of guesswork: any gap *inside* a row's printed content is given literally, position and all.
- **What's left is narrower: only the *unprinted* padding beyond the first and last printed run, on rows whose total (including any interior `-` runs) falls short of that row's max capacity.** Loomerly doesn't print leading/trailing blank runs, only the "meaningful" bounded content — e.g. `Row 3 (→) (3)B, (14)-, (3)B` sums to 20, but this piece's full half-width (established from un-tapered interior rows like Row 17, which sums to exactly 28) is 27 or 28 depending on parity — so 7-8 beads of invisible padding exist beyond both printed ends and need to land somewhere. Two things now support centering specifically (not just "it looks symmetric" as before): the picture-chart image is unambiguously mirror-symmetric left-to-right, and the paired rows are short by the *same absolute amount* from their respective max capacities (Row 3: 27−20=7; Row 4: 28−21=7) — exactly what a symmetric trim produces, and not something a left- or right-aligned trim would. Centering (`start = floor((rowCapacity − rowTotal) / 2)`) is now a well-supported default, not just a guess, though still worth a final pixel-level cross-check against a picture-chart page during the geometry spike rather than shipped purely on this reasoning.
- **Interleave order for unequal-length pairs** — confirmed consistent with the peyote-shaping expectation: paired rows differ in total by at most 1 within the interior, and the generalized "alternate while both have beads left, then append whichever remains" interleave (from the original plan) still applies once each half's printed runs (including its own interior `-` runs) are expanded to a flat per-bead list first.
- **`Starting bead: Top Right` + per-row `→`/`←` arrows remain Loomerly's own explicit reading-direction data for each line** — trust the printed arrow per row, don't re-derive it.

Recommended first build step, before any of the storage/UI work below: a small standalone Node script that runs the pairing + centering + interleave hypothesis against this exact sample's full word chart, and a manual visual comparison of the reconstructed grid against the picture-chart page. Cheap to build, and it's the one thing in this plan that would be expensive to get wrong silently (a warped, unusable pattern that still "imports successfully").

## Decisions

- **PDF text extraction via a vendored copy of pdf.js (Mozilla), not a CDN, not hand-rolled parsing.** This is the first genuine third-party dependency in the codebase (Decision #2 was about UI frameworks specifically — this is a narrow, isolated parsing utility, not a UI library, and it's dynamically `import()`-ed only when the user actually triggers an import, so it costs nothing on every other page load). Vendor pdf.js's prebuilt `pdf.mjs`/`pdf.worker.mjs` as static files under `/vendor/pdfjs/` (no bundler needed — pdf.js ships as ready-to-use ES modules) so the app stays fully self-contained/offline-capable for iPad home-screen use, rather than depending on a CDN being reachable. Worth a follow-up note in CLAUDE.md's Decision #2 once this ships, since it's a real (if narrow, deliberate) exception.
- **Color codes are never auto-resolved to hex.** Loomerly's color list gives a Miyuki catalog number and name (e.g. `M137 Transparent Light Orange`) but no hex — and this app has no catalog→hex data source (the same unresolved gap as CLAUDE.md's Bead Specs section, 900+ SKUs with no machine-readable source). Import always pauses on a color-assignment step where the user picks a hex per unique code, via the exact same native `<input type="color">` + Phase 8 `customColorStore` flow already built for manual palette entry — no new color-picking UI, just a new entry point into it.
- **Bead type is guessed, shown, and confirmable — not silently auto-detected.** The color list's header line (`"Miyuki Rocailles 11/0 (M)"` → `rocaille11`, `"Miyuki Delica 11/0 (M)"` → `delica11`) is read when present and used as the guess. When it's absent (confirmed this session: not every real export has it — see the geometry section above), fall back to comparing predicted finished size for both bead types (via `generatePeyoteGrid`) against the PDF's own stated finished size and guessing whichever is closer. Either way, the guess is shown on the preview screen as a normal choice the user can override before continuing — never a silent, unconfirmable decision (Decision #7 still bounds the choice to just these two bead types).
- **The importer writes directly to a new design record via `designStore`/`colorwaySync`-shaped data, bypassing live `appState`/`cellStore` entirely.** This is a one-shot batch reconstruction, not interactive editing — there's no live canvas to route through. Once the record's saved, the user opens it exactly like any other design; nothing about the editor needs to know it was imported.
- **No automatic reuse of a previously-imported color across designs in v1.** Every import creates fresh `customColors` entries for its codes, even if an identical Miyuki number was already assigned a hex in an earlier import. Matching by catalog number to offer "reuse this color" is a real, valuable fast-follow (avoids palette bloat across repeated imports) but adds real scope (fuzzy/exact matching UI, catalog-number storage on `customColors` which doesn't exist today) — deferred, logged below.
- **Validation is a warning, not a hard stop**, consistently with Phase 5/6's existing philosophy: bead-type mismatch and unsupported section count/stitch type do block (there's no sane partial import), but a finished-size or total-bead-count mismatch against the PDF's own header stats surfaces as a visible warning on the pre-import preview screen, import still proceeds if the user confirms.

## File-by-file breakdown

### `/vendor/pdfjs/` (new, static files)
Prebuilt `pdf.mjs` + `pdf.worker.mjs` from a pinned pdf.js release, committed as-is (no build step, matches this repo's existing no-bundler approach). `GlobalWorkerOptions.workerSrc` points at the local vendored worker file.

### `src/import/pdfText.js` (new)
```js
export async function extractPdfPageTexts(arrayBuffer) // => string[], one entry per page
```
Thin wrapper: loads the document via pdf.js, calls `getTextContent()` per page, joins each page's text items in reading order. No parsing logic here — just "give me the text."

### `src/import/loomerlyParser.js` (new, pure)
```js
export function parseLoomerlyExport(pageTexts) // => ParsedPattern | { error }
```
- Locates the header stats page (`Type:`/`Width:`/`Height:`/`Finished size:`/`Total beads:` lines), the word-chart pages (concatenated until the `Color List` header), and the color-list page, by content match — not fixed page indices, since page count varies with pattern length.
- Validates `Type: Peyote` and `Section 1 of 1` up front; returns a typed error otherwise (surfaced verbatim in the UI, not swallowed).
- Word-chart line grammar: `Row (\d+)(?:&(\d+))? \((→|←)\)\s+(.+)`, capturing row number(s), direction, and a run-list tail. Run-list tail is either `-` (zero beads) or a comma-separated `(\d+)CODE` list (`CODE` matches this app's own `A`.."Z","AA".. scheme from `colorCodes.js` — read as literal text here, no need to re-derive the assignment, Loomerly already assigned it).
- Color-list page: header line for bead type detection, then repeating `CODE / M-number / Name / Count: N` blocks.
- Returns `{ meta: {width, height, finishedSizeIn, totalBeads}, startingBead, rowEntries: [{rowNumbers, direction, runs}], colors: [{code, catalogNumber, name, count}], beadTypeKey }`.

### `src/import/loomerlyImport.js` (new, pure)
```js
export function buildGridFromLoomerly(parsed) // => { rows, cols, shapeEntries, colorEntries: [[key, code], ...] }
```
- `rows = parsed.meta.width`, `cols = parsed.meta.height`.
- Groups `rowEntries` into consecutive pairs by row number (handles Loomerly's pre-combined "Row 1&2" line and plain "Row N"/"Row N+1" pairs identically — grouping is by parsed row *numbers*, not by how many text lines they came from).
- Per pair → one `col`: un-reverses each half's run list back to canonical order per its own `←`/`→`, decodes runs into a flat per-bead list per half (a `-` run decodes to that many literal blank/unoccupied positions inline, same as a color run — only difference is nothing gets written to `shapeEntries` for those positions), interleaves the two halves (alternating while both have beads, then appending whichever remainder is left), centers the combined list within `[0, rows)` to place any *remaining* (unprinted, edge-only) padding, and writes each non-blank bead as a `shapeEntries` key + a `colorEntries` entry keyed by the *code* (not yet a real `colorId` — that substitution happens after the color-resolution step, see below). Blanks from an interior `-` run and blanks from outer centering padding end up identical in the output (both are just an absent `shapeEntries` key) — the distinction only matters during parsing, not in the reconstructed grid.
- Pure and independently testable with hand-written fixtures — this is where the geometry derivation above gets encoded and regression-tested, including a fixture built from this exact sample's numbers.

### `src/ui/importDialog.js` (new)
Three-step flow, invoked from a new "Import" action in `libraryView.js`'s header (alongside "+ New"):
1. **File pick** (`<input type="file" accept=".pdf">`) → read as `ArrayBuffer` → `extractPdfPageTexts` → `parseLoomerlyExport`. Parse failure shows the error and stops here.
2. **Preview** — pattern name/type/dimensions, computed finished size vs. the PDF's stated finished size (the sanity check from the geometry section above, shown as a warning if they diverge past a generous tolerance), total reconstructed bead count vs. stated `Total beads`, and the list of colors found (code, catalog number, name, count). Cancel or Continue.
3. **Color resolution** — one row per unique code from step 2, each with a native `<input type="color">` (no default — forces a deliberate choice, consistent with Phase 8's "no colors yet" empty state having no default either) and the code's catalog number/name/count shown as context. Confirm is disabled until every code has a color picked. On confirm: creates one `customColors` entry per code (named from the catalog name, e.g. "Transparent Light Orange") via the existing `customColorStore.createCustomColor`, substitutes real `colorId`s into the `colorEntries` from step 1's grid data, then calls `designStore.createDesign` + `saveDesign` to write the finished record (name taken from the PDF's own title field, user can rename afterward via the existing library rename action — no special-case needed), and opens it.

### `libraryView.js` / `main.js`
New "Import" button next to "+ New" in `#library-header`, wired to mount `importDialog.js`'s flow; on success, same `appState.designs` in-place update + `openDesign()` pattern every other library mutation already uses (no full re-fetch).

## Testing strategy

- `loomerlyParser.js` and `loomerlyImport.js` are pure text-in/data-out — fully covered by `node:test` with hand-written word-chart text fixtures (no PDF library needed in Node at all): combined-pair parsing, plain-pair parsing, direction reversal, shaping/centering, unequal-length-pair interleave, the `-` empty-row case, bead-type detection, and the malformed/unsupported-format error paths.
- A strong regression case: take an existing design already in this app, run it through this app's own `buildWordChart`/`printView` text generation, and feed that text back through `loomerlyParser.js`/`loomerlyImport.js` — confirm the reconstructed cells match the original exactly. This app's own word-chart format is close to a subset of Loomerly's (same run-length-encoding, same combined-first-pair idea), so this is a meaningful check that doesn't require a real PDF, and catches regressions in the geometry logic independent of the PDF-parsing layer.
- `pdfText.js` (the actual PDF-library integration) has no meaningful `node:test` coverage — verified in headless Chromium via Playwright instead, same as every other DOM-dependent module in this project, run against the real sample PDF(s) saved into the repo (suggest `.work/samples/`).
- The geometry validation spike (recommended as build step 1, see above) should be written as a disposable script, not shipped — its job is to build confidence before the real pure functions are written, not to be permanent test coverage.

## Build order

1. **Geometry validation spike** (disposable script) — confirm the pairing/centering/interleave hypothesis against the one real sample, manually cross-checked against the picture-chart page.
2. `loomerlyParser.js` + its `node:test` suite (text-in/data-out, no PDF dependency yet — write fixtures by hand from the sample's actual text).
3. `loomerlyImport.js` + its `node:test` suite, including the buildWordChart-round-trip regression case.
4. Vendor pdf.js, build `pdfText.js`, verify text extraction against the real sample PDF(s) in Playwright.
5. `importDialog.js` (all three steps) + `libraryView.js`/`main.js` wiring.
6. Full Playwright pass: import the real sample end-to-end, confirm the resulting design's pixels match a manual trace of a few known rows/colors from the PDF, confirm it opens/saves/prints normally afterward like any other design.
7. Real iPad pass — file-picker UX for selecting a PDF from Files/iCloud in Safari is untested territory for this project (Phase 4's file-picker precedent was Photo Trace's image picker, a different picker UX).

## Open questions / deferred

- **Sample coverage is now good.** Four real samples gathered this session: the original tapered single-color piece, two plain rectangles (one solid, one 3-color), and a multi-taper 4-color lattice/tessellation piece with genuine interior negative space. Between them: the core `rows=Width`/`cols=Height`/pairing hypothesis is confirmed exactly (not approximately) via the rectangles; interior blanks are confirmed to print as literal `-` runs via the lattice piece; multi-color run parsing is exercised by both colored samples; and outer-edge centering for tapered rows is well-supported (symmetric picture + equal trim amounts) though still not pixel-exact-confirmed. The one thing no sample has exercised: a pattern where the bead-type header is *absent* **and** the finished-size guess is genuinely ambiguous between Delica/Rocaille (both samples missing the header so far were solid rectangles with a fairly clear best fit) — low-risk, the UI-confirm step covers it either way, not worth blocking on.
- **Save the actual PDF files into the repo** (suggest `.work/samples/`) before implementation starts — everything checked this session was against extracted text/images pasted into the conversation, not real files on disk, and the plan's Playwright verification step needs real files to run pdf.js against.
- **Color reuse across imports** (match an already-created `customColors` entry by catalog number instead of always creating a new one) — real value, real scope, deferred to a fast-follow.
- **Non-peyote Loomerly exports** (brick/square/loom) — this app doesn't have those grid types yet either (CLAUDE.md's Later/optional backlog), so out of scope until/unless those grid types get built.
- **Multi-section Loomerly patterns** — explicitly rejected with a clear message in v1, not attempted.
- Whether Loomerly's PDF is even the best source vs. some other export format Loomerly might offer (CSV, a plain text file) — worth a quick check next time the user is in Loomerly, since a structured text/CSV export (if one exists) would remove the entire pdf.js dependency and the PDF-page-boundary parsing complexity for free. Not blocking — the PDF path works and is scoped — but worth 30 seconds of checking before investing in the pdf.js vendoring step specifically.
